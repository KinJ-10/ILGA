作成日：2026-09-09
対象：ILGA / VIEWER

## 1. 文書の目的・v0.1の対象範囲

開発担当者が、社内説明・学習・引継ぎで「何を取得し、どの条件で検出し、何を計算するか」を確認するための文書です。

対象は**右足の甲付近、現在の装着向き、10m歩行**です。1台のTAGから得た右足の運動を使います。
装着の向きは自動判定しません。別の足・足裏・別の向きに、そのまま同じ条件を適用する想定ではありません。
医療診断、解剖学的に精密な接地時刻の推定、個々の歩幅推定、TUGは対象外です。

画面の「右足の歩行周期検出数」は右足イベントの数であり、左右すべての歩数を直接検出した数ではありません。

## 2. アプリ全体構成

PowerShellでWindowsのPython 3.12を起動し、PythonがBLE受信とローカルHTTPサーバを担当します。
ブラウザのHTML/CSS/JavaScriptはボタン操作をサーバへ送り、受信状態や結果を表示します。
測定終了後、Pythonから既存の機能歩行解析器を呼び出します。exe化はしていません。

サーバは**127.0.0.1のみ**で待ち受けます（標準ポート8765）。
測定データは同じPC内のファイルに保存し、アプリに外部サービスへのデータ送信処理はありません。
初回の依存パッケージ導入は別途ダウンロードを伴うため、「導入時も通信不要」という意味ではありません。
BLEによるTAG→PC通信と、ブラウザ→同じPCのHTTP通信は行います。

主要12ファイルはすべて [VIEWER/python/gait_demo_app](../VIEWER/python/gait_demo_app/) 内です。

## 3. 処理フローと保存物

```text
PowerShell起動 → Pythonローカルサーバ → ブラウザで取得開始
  → TAG探索・BLE接続 → 100Hz相当の正常受信 → sensor.csvへ逐次保存
                           └ 受信中にSTART→FINISHを別CSVへ記録
  → 最初の正常受信から標準30秒で終了（手動停止も可）
  → 既存解析器 → analysis.json・waveform.png・report.html
  → 結果欄の絶対パス／保存フォルダーを開く
```

「100Hz相当」は目標・受入確認項目であり、BLE接続成功だけで保証されるものではありません。
探索・接続時間は30秒に含みません。受信とマーカー記録は並行して行います。

| 保存物 | 意味 |
|---|---|
| `sensor.csv` | seq、PC受信時刻、加速度3軸（mg）、角速度3軸（mdps）。重複や無効値を除外した受信データ |
| `markers.csv` | 操作者が押したSTART/FINISHの時刻。Web入力でも互換スキーマのsourceはoperator_key、notesはweb_button |
| `metadata.json` | 装着条件、距離、取得設定、実測歩数、開始足・終了足、足踏み自己申告、受信状態など |
| `analysis.json` | 既存解析結果と表示用demo項目。技術フィールド名は互換性のため英語のまま |
| `waveform.png` | 6軸波形、START/FINISH、採用された右足イベント |
| `report.html` | 日本語結果。波形→指標→測定状態の順。PNGは同じフォルダーを参照 |

測定ごとに日時と識別子の付いた `runs/` の新規フォルダーを作ります。
既存解析器の詳細CSVなどは `analysis_<識別子>/` に保存します。
実測歩数等の更新では表示用結果を再生成しますが、元のsensor.csvとmarkers.csvは保持します。
通信切断やマーカー不足でも、取得済みデータと解析不可・警告を示す成果物を残します。
ディスク容量不足など、保存そのものが失敗する場合は例外です。

同期用足踏みは開始前・終了後各3回を案内します。回数は自己申告で、自動検出ではありません。
不足・未確認でも解析を継続して警告します。本アプリの区間決定には動画との時計同期を使いません。

## 4. 検出方式の考え方

検出するのは接地そのものではなく、**右足の繰り返し運動を示すstride marker（歩行周期マーカー）**です。
右足の運動中の「正の回転の山→負方向への切替え→十分な負の回転」という波形パターンを探します。
正式候補の代表時刻は、後述する正→負のゼロ交差時刻です。

`gx` はセンサーX軸まわりの角速度です。現行コードはKin/doi解析で固定したgx候補を再利用しています。
現在の装着条件で観察した右足運動の特徴を使う設計であり、gxがあらゆる装着で最適だと証明したものではありません。
装着を回すと軸成分の配分や正負が変わり、同じ動きでも条件を満たさなくなります。
したがって「X軸＝常に解剖学的な同じ軸」と解釈しないでください。

## 5. 現在の固定検出条件

以下は `evaluate_gait_events.py` の定数と `detect_fixed_candidates()`、
および機能歩行解析器の区間採用処理で照合しました。振幅条件は**フィルタ後のgx**に対して判定します。

| 項目 | 現行値・判定 | 意味 |
|---|---|---|
| 時間グリッド | 100Hz、1 seq = 0.01秒 | seqの増分を時間に換算する。受信の到着間隔とは別 |
| フィルタ | 4次Butterworth、5Hzローパス、filtfilt | 高周波成分を抑え、前後方向処理で位相ずれを打ち消す |
| 正ピークの高さ | 80 dps以上 | 正方向に十分な角速度を持つ山を残す |
| prominence | 50 dps以上 | 周囲の谷に対して十分に際立った山を残す |
| ピーク間隔 | 0.75秒以上（75サンプル） | 近接する山の重複検出を抑える。最終マーカー間隔そのものの下限ではない |
| 正→負ゼロ交差 | ピーク後0.30秒以内 | 正方向の運動から負方向へ切り替わることを確認 |
| 負方向の確認 | ゼロ交差後0.40秒以内に−50 dps以下 | 小さなゼロ付近の揺れでなく、十分な逆方向運動であることを確認 |
| 区間採用 | START ≦ 対応する受信時刻 ≦ FINISH | 有効な歩行区間内の正式候補だけを数える |

処理順は、seqの巻戻り処理・欠番の線形補間→フィルタ→正ピーク→ゼロ交差→負方向確認→区間採用です。
欠番を補間しても、失われた実測値が復元されたわけではありません。欠損情報は確認項目に残ります。

ゼロ交差は隣接点の `gx[i] > 0` かつ `gx[i+1] <= 0` で検出し、時刻を直線補間します。
0.30秒は30サンプル相当、0.40秒は40サンプル相当です。
厳密な実装では負方向確認窓はゼロ交差の直後側サンプルから数えるため、連続時間の説明とは最大1サンプル程度の差があります。

4次は片方向のフィルタ設計次数です。filtfiltは前後2回処理するため、合成された振幅応答は片方向と同一ではありません。
未来のサンプルも使う**ゼロ位相・オフライン解析**であり、そのままリアルタイムの検出遅延評価には使えません。

## 6. 各値の意味と由来

5Hz、80/50/−50 dps、0.75/0.30/0.40秒は、**Kin/doi GA Phase1-aの実測解析を基に固定した工学的な暫定値**として扱います。
コード冒頭はKin/doiのパラメーターを `without tuning` で使うと明記し、
[既存評価文書](ga/GA_OFFLINE_EVALUATION.md)も入力を見た自動閾値調整を行わないとしています。
被験者・歩行速度に応じた自動調整はありません。

特に**5Hzを特定文献値の直接採用と断定しません**。照合したコード・文書には、その対応を裏付ける出典は示されていません。
一般的な設計意図は、歩行の基本的な周期と波形変化を残しながら、高周波の振動や細かな揺れを抑えることです。
これは値の考え方であって、5Hzが全員・全速度に最適である根拠ではありません。

振幅閾値は「動きの大きさ」、prominenceは「周囲からの際立ち」、時間窓は「パターンが続く速さ」を制限します。
値を固定することで比較の再現性は得られますが、低速・別装着への適合は別途評価が必要です。

## 7. 計算式と実測／参考の区別

### 7.1 歩行時間と速度：PC時計

```text
歩行時間 T [秒] = (FINISHのmarker_monotonic_ns − STARTのmarker_monotonic_ns) / 10^9
歩行速度 v [m/s] = 10 [m] / T [秒]
```

操作者の反応とWeb要求の処理遅延を含みます。TAG内部の取得時刻を直接測った値ではありません。

### 7.2 右足周期と歩行テンポ：seq時計

採用された右足マーカーのseq由来時刻を t₁, t₂, …, t_R とします。

```text
右足周期 Δᵢ [秒] = tᵢ₊₁ − tᵢ          （区間数はR−1）
代表周期 = median(Δᵢ)
歩行テンポ [歩/分] = 120 / 代表周期 [秒]
120 = 60 [秒/分] × 2 [歩/右足周期]
```

右足から次の右足までを、左右交互歩行の約2歩に対応させます。
現行実装は周期の**中央値**からテンポを計算します。マーカー2個未満では周期・テンポを算出しません。
イベントが歩行区間に入るかはseq時刻をPC受信時刻へ対応付けて判定し、周期の計算自体はseq時計を使います。

### 7.3 参考総歩数

Rを「区間内で採用された右足マーカー数」とすると、既存解析器の換算は次のとおりです。

| 開始足 | 終了足 | 参考総歩数 |
|---|---|---|
| 右 | 右 | 2R−1 |
| 左 | 左 | 2R+1 |
| 右 | 左 | 2R |
| 左 | 右 | 2R |

開始足・終了足が不明なら、既存解析器は換算値を未算出にします。
アプリの表示層だけで2Rの概算を示し、境界の歩数を補正できないことを警告します。
マーカーが得られない・区間が無効な場合は参考総歩数を表示しません。
この換算は、左右交互の歩行と右足イベントが適切に得られることを前提にします。

### 7.4 距離とばらつき

```text
平均歩幅・実測歩数由来 [m] = 10 / 入力した実測歩数
平均歩幅・参考 [m]         = 10 / 参考総歩数
平均歩行周期距離・参考 [m] = v × mean(Δᵢ)
CV [%]                    = 100 × 周期の標本標準偏差 / 周期の平均
```

実測歩数は人が数えた任意入力で、推定値とは別欄です。未入力をゼロ歩として扱いません。
平均歩幅は区間平均であり、1歩ずつの距離を求める処理ではありません。
平均歩行周期距離も区間速度と平均周期の積による参考値です。

主表示の「歩行周期のばらつき」は、周期が試行中央値の**0.70〜1.50倍（両端含む）**の区間だけを使うCVです。
全区間のCVも別表示します。標本標準偏差には少なくとも2区間が必要です。
周期が中央値の1.50倍を超え、かつ中央値より0.50秒以上長いと「停止または見逃し」の確認対象にします。
両者をこの条件だけで区別することはできません。画面ではCVという略語を表示していません。

## 8. 低速歩行の取りこぼし

遅く小さな動きでは、80 dpsのピーク高さ、50 dpsのprominence、−50 dpsの負方向条件を満たしにくくなります。
回転の切替えが遅ければ0.30秒のゼロ交差窓、0.40秒の負方向確認窓から外れる可能性もあります。
これは影響し得る要因であり、特定の見逃し原因は候補ごとの失敗理由と波形で確認する必要があります。

既存の2026-09-03低速右足例 `slow_right_01` は、**実測16歩、右足marker 3個、参考6歩**です。
通常例は16歩／8個／16歩、高速例は14歩／7個／14歩です。低速例の差をv0.1で補正してはいません。

閾値を下げたり時間窓を広げたりすると見逃しが減る可能性がありますが、
装着調整・足踏み・旋回などの動作まで拾う誤検出が増える可能性があります。
改善時は通常・低速と非歩行動作を比較し、既存条件からの変更を明示して評価します。

## 10. 次の簡易評価計画

まず通常10mを最低1試行、可能なら**通常2試行・低速1試行**を取得します。
各試行で実測歩数、開始足、終了足、測定名を記録します。
1試行だけでは再接続の合否を判定できないため、v0.1受入完了には2回目取得も必要です。

1. TAG探索・BLE接続、受信件数、最終受信Hz、データ欠損、無効値、センサー異常を確認する。
2. START→FINISHを記録し、歩行時間、右足marker数、参考歩数と実測との差を確認する。
3. 30秒自動終了と6保存物、実測／参考表示の区別を確認する。
4. 1回目終了後に再接続・2回目取得を確認する。
5. 別の静止試験で受信後にTAG電源を切り、日本語エラーと取得済みデータ保持を確認する。

[READMEの実機受入チェックリスト](../VIEWER/python/gait_demo_app/README.md)の合格目安は、
終了時95〜105Hz、欠損・無効値0、異常なし、正の歩行時間がマーカー差と整合、
正常受信から約30秒で終了（最終受信経過29.5〜30.5秒）、6保存物、2回目取得、エラー時保持です。
このHz・時間幅はデモ受入の目安であり、センサー精度を保証する規格値ではありません。

**v0.1の操作・取得・保存の合格と、低速検出改善は別課題**です。
参考歩数の実測一致をアプリ動作の合格条件にはせず、不一致も隠さず記録して解析性能の評価につなげます。

Miura01は低速・小振幅で3件不足しました。Miura02はSTARTの0.188秒前の小ピークが63.7 dps、
Miura03はSTART後の小ピークが60.0 dpsで、いずれも80 dps未満でした。
Miura04では終端候補96.3 dpsが現行条件を通り、直前間隔は2.023秒でした。
終端足のmetadataも実歩数・開始足と不整合です。したがって、**固定閾値を単純に下げません**。
低下させるとMiura04のような終端・非歩行動作も取り込みやすくなります。

既知の制限は、低速歩行、小振幅・すり足、最初の一歩、終端調整、START/FINISHの操作遅延です。
次の改善では、個人キャリブレーションを調整用試行と未使用検証試行に分け、
初動・定常・終端を別状態として扱うことを検討します。通常歩行向けの厳密条件は維持します。

詳細な再評価の根拠は、
[2026-09-10歩行デモ6試行再評価レポート](../analysis_out/gait_demo_20260910_review/report_ja.md)を参照してください。

## 12. 用語集

| 用語 | このアプリでの意味 |
|---|---|
| 角速度 | 回転の速さと向き。gxはセンサーX軸まわりの成分 |
| dps | degrees per second、度/秒。CSVのmdpsを1000で割るとdps |
| ローパス | 低い周波数成分を通し、高い周波数成分を抑えるフィルタ。境界で突然すべて消えるわけではない |
| ピーク | 波形の局所的な山。高さと周囲からの際立ちは異なる |
| prominence | 山頂から、左右の基底のうち高い側が作る基準高さまでの差。単なるゼロからの高さではない |
| ゼロ交差 | 波形が0をまたぐこと。ここでは正から0以下への切替え |
| 歩行周期 | 同じ足のイベントから次の同じ足のイベントまで。左右交互なら概ね2歩に相当 |
| CV／ばらつき | 標準偏差÷平均を百分率にした値。小さいほど周期が揃うが、検出が正確である証明にはならない |
